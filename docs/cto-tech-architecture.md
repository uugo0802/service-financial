## 1. e-Tax / eLtax 外部連携方式の調査結果

### 1.1 e-Tax（国税・国税庁）

**民間連携APIの提供有無**
- 国税庁は「国税電子申告・納税システムAPI」をHTTPベースで提供している（[国税電子申告・納税システムAPIの概要](https://www.e-tax.nta.go.jp/shiyo/api.htm)）。
- ただし用途は限定的：**基本情報（氏名・住所等）や各税目の登録情報の「照会（参照）」が中心**で、「ほとんどのAPIは参照のみで更新不可」「**認証および申告データの送信はAPIでは提供されていない**」（同ページより）。
- ソフトウェア開発業者はAPI利用のためAPIキー発行申請が必要（[ソフトウェア開発業者の方へ](https://www.e-tax.nta.go.jp/shiyo/index.htm)）。
- 結論: **e-Tax APIは「申告書データの送信」には使えない**。送信は別の仕組み（下記1.3）で行う。

**認証方式**
- 個人：マイナンバーカード（公的個人認証サービス＝JPKI の電子証明書）または利用者識別番号＋暗証番号方式。
- 法人：法人代表者の電子証明書、または利用者識別番号方式。
- 公的個人認証サービス（JPKI）は2016年の法改正で**民間事業者による署名検証が解禁**されているが、利用には主務大臣認定が必要（[総務省: 公的個人認証サービスによる電子証明書（民間事業者向け）](https://www.soumu.go.jp/kojinbango_card/kojinninshou-02.html)）。スマホ用電子証明書についても同様に民間事業者側で主務大臣認定が要る（[公的個人認証サービスポータル](https://www.jpki.go.jp/)）。
- → **カイの整理**: freee/MFはこの認定を取得しているか、あるいは「利用者本人のブラウザ/PC/スマホ内で完結する署名処理」に閉じることで認定を回避する設計にしている可能性が高い。要調査（後述の要確認事項）。

**申告データの標準フォーマット**
- 従来はXML形式が基本。近年は法人税申告書別表・勘定科目内訳明細書等で**CSV形式での提出も選択可能**になっている（[法人税申告書別表等のデータ形式の柔軟化(CSV形式)](https://www.e-tax.nta.go.jp/topics/2019/topics_oshirase_310228.htm)）。
- 民間会計ソフトが生成した申告データは拡張子 **`.xtx`** 形式（e-Taxソフト（WEB版）が読み込める形式）としてやり取りされる（[e-Taxソフト(WEB版)FAQ](https://www.e-tax.nta.go.jp/toiawase/qa/e-taxweb/49.htm)）。
- 送信時には電子署名を付与し、政府認証基盤（GPKI）と相互認証された認証局発行の電子証明書を添付する必要がある（[電子証明書の取得](https://www.e-tax.nta.go.jp/systemriyo/systemriyo2.htm)）。
- 仕様書は「e-Tax仕様書一覧」からCAB形式でダウンロード可能（要解凍）。令和7年5月時点でも定期的に更新・公開されている（[e-Tax仕様書等の掲載について](https://www.e-tax.nta.go.jp/topics/2025/topics_20250515_shiyo.htm)）。

**既存会計ソフトの連携実装（freee/MF）**
- **freee**: 「確定申告」メニューから「電子申告（freee）」を選ぶと、freeeの電子申告アプリが本人のマイナンバーカード（電子証明書）をPC/スマホで読み取り、申告書類データに電子署名を施したうえでe-Taxシステムへ直接送信する（[freee e-Tax連携](https://www.freee.co.jp/accounting/individual/purpose/e-tax/)）。つまり**freee自身が「e-Tax対応ソフトウェア」として国税庁の認定を受け、xtx相当のデータ生成から署名・送信までを自社アプリ内で完結**させている。マイナンバー自体はfreee側のサーバーに送信されず、ローカル（利用者のPC/スマホ）で署名処理が行われる設計と推測される。
- **マネーフォワード クラウド確定申告**: 決算書・確定申告書を作成後、①電子申告用データ（xtx形式）をダウンロードしe-Taxソフトへインポートして送信する方式と、②スマホアプリでマイナンバーカードを読み取り申告書作成から提出まで完結させる方式の2通りを提供（[MF e-Tax連携](https://biz.moneyforward.com/support/tax-return/tax-return-guide/bs2/bs208.html)）。①は「MFはデータ生成のみ、送信はe-Taxソフトという別ソフトが担当」という最もシンプルな構成で、**自社をe-Tax対応ソフトとして認定登録する必要がない**。

**カイの技術的結論（Phase 1設計への反映）**
1. MVPでは**MFパターン①（xtx/CSV/XMLファイルを生成し、e-Taxソフト（WEB版）へインポートしてもらい、本人操作で送信）**を採用するのが最速・最安。自社をe-Tax対応ソフトとして認定登録する手間・審査期間（freeeパターン）はPhase 3以降の検討事項とする。
2. これにより「送信手順ガイド」は具体的には：①下書きデータをe-Tax標準の.xtx/CSV形式で出力 → ②ユーザーがe-Taxソフト（WEB版）にログイン → ③ファイルを読み込み → ④マイナンバーカードで電子署名 → ⑤送信、という5ステップのスクリーンショット付きガイドUIを作ればよい。API連携は不要。
3. **要調査（今週中）**: e-Taxソフト（WEB版）がインポート可能な「.xtx」ファイルの正確な生成仕様（申告書ごとのXML/CSVスキーマ）。国税庁「e-Tax仕様書一覧」からのダウンロードには時間がかかるため、開発着手前にダウンロード申請を行う（下記タスクリスト参照）。

### 1.2 eLTAX（地方税・地方税共同機構）

- eLTAX対応ソフトウェアを開発する民間事業者向けに、地方税共同機構が「送受信モジュール」「電子署名モジュール」等のAPI/モジュールを提供している（[eLTAX対応ソフトウェアを開発される方へ](https://www.eltax.lta.go.jp/support/software/)）。
- これらのAPI・モジュール・仕様書は**著作権保護対象**であり、利用には地方税共同機構への申請・審査が必要（詳細フローは公式ページで要確認、WebFetchが403で弾かれたため詳細は開発者登録後にしか見られない可能性がある）。
- 公式クライアントとして「PCdesk」「PCdesk Next」が提供されており、Web版とインストール版がある（[PCdeskの特徴と取得方法](https://www.eltax.lta.go.jp/eltax/software/)）。
- 仕様書・様式は「仕様書・様式集」ページで公開（[仕様書・様式集](https://www.eltax.lta.go.jp/support/shiyosho/)）。
- **カイの結論**: eLtaxもe-Taxと同様、MVPでは「PCdesk（Next）にインポート可能な形式でデータを出力し、本人がPCdeskで電子署名・送信する」方式を採用。マイクロ法人向け機能（Phase 1では消費税・法人税の**概算試算のみ**）では送信フロー自体はPhase 1スコープ外なので、当面は仕様理解を最小限にとどめ、Phase 2（マイクロ法人の消費税・法人税申告対応）着手前に地方税共同機構への開発者登録を行う。

### 1.3 認証まわりの要調査事項（専門家/実機検証が必要）

1. freeeが「e-Tax対応ソフトウェア」の認定をどのフローで取得したか（審査期間・要件）→ Phase 3でAPI直接連携を検討する際の前提調査。
2. マイナンバーカード読み取り・署名処理を自社アプリ内で行う場合と、e-Taxソフト（外部アプリ）に委ねる場合とで、**税理士法上の「代理」に該当するリスクの違いがあるか**（本人操作である限りリスクは同じはずだが、要弁護士確認）。
3. スマホ用電子証明書（マイナンバーカードのスマホ搭載機能）をMVPでどこまでサポートするか（対応にはデジタル庁/総務省への追加申請が必要な可能性）。

## 2. MVP技術スタック案（低ランニングコスト最優先）

設計方針: **サーバーレス・従量課金・固定費ゼロに近い構成**。ユーザー数が少ない立ち上げ期は月額数千円〜1万円程度に収まる構成を狙う。

| レイヤ | 選定 | 理由 |
|---|---|---|
| フロントエンド | Next.js（App Router）+ TypeScript + Tailwind CSS | 開発速度、SSR/SSG、エコシステムの厚さ |
| ホスティング（FE） | Cloudflare Pages（または将来Vercel Pro） | 無料枠が寛大、エッジ配信、コールドスタート課金なし |
| バックエンドAPI | Cloudflare Workers（Hono framework）or Next.js Route Handlers | サーバーレス、リクエスト課金のみ、常駐サーバー不要 |
| DB | Supabase（Postgres + Auth + Storage + Row Level Security） | マネージドPostgres、無料〜$25/月から開始、RLSでマルチテナント設計が容易 |
| ファイルストレージ | Cloudflare R2 | 明細CSV・レシート画像・生成した申告書PDF/XMLの保存。**エグレス（送信）課金がゼロ**なのがR2最大の利点 |
| 非同期処理・キュー | Cloudflare Queues（または Supabase Edge Functions + pg_cron） | 明細取り込み〜AI仕訳のバッチ処理を非同期化、レイテンシ要件を緩めてコスト最適化 |
| 認証 | Supabase Auth（メール+マジックリンク、将来2要素認証） | 別途Auth0/Clerk等の月額固定費を避ける |
| AI/LLM | Anthropic Claude API（Haiku 4.5 / Sonnet 5 / Opus 4.8 のハイブリッド運用、詳細は3章） | 従量課金、Batch API併用でさらに50%減 |
| 監視・ログ | Cloudflare Analytics + Supabase Logs（+ Sentry無料枠） | 固定費最小 |
| CI/CD | GitHub Actions（無料枠） | — |

**明細取り込み方式（Phase 1）**
- 第一段階: **CSV手動アップロード**のみ（銀行・カード会社ごとのCSVエクスポート機能を利用）。外部API利用料が発生しないため最安。主要ネット銀行・カード会社（住信SBI、楽天銀行、GMOあおぞら、三井住友カード、楽天カード等）のCSVフォーマットを個別にパーサ実装。
- 第二段階（Phase 1後半〜Phase 2）: 銀行API連携アグリゲーター（Moneytree LINK等）の導入を検討。ただしAPI利用料が月額固定費として発生するため、有料プラン契約者が一定数を超えてから導入判断する（ランニングコスト最小化の思想と整合させる）。

**ホスティングコストの目安（超概算・MVP初期）**
- Cloudflare Pages/Workers: 無料枠内〜数百円/月
- Supabase: 無料枠〜Pro $25/月
- Cloudflare R2: 数百円/月（保存量次第、エグレス無料が効く）
- Claude API: 利用量次第（3章で詳述、Haiku中心なら数千円/月から）
- 合計: 立ち上げ期は月額1〜2万円程度に収まる設計を狙う

## 3. AI自動仕訳パイプライン設計方針

business-planの差別化ポイント「AIによる仕訳の自動確定率を最大化、人間のレビューは例外処理のみ」を実現するため、**ルールベース→LLMのハイブリッド2段構成**とする。

### 3.1 パイプライン構成

```
[取込明細 1行] 
   → ①正規化（日付・金額・摘要文字列のクレンジング）
   → ②ルールベース照合
        - ユーザー固有の過去仕訳履歴との完全一致/部分一致（摘要文字列パターン）
        - 勘定科目辞書（頻出取引先・キーワード辞書、インボイス登録番号マッチ等）
   → ③ルール一致 → 勘定科目・税区分を自動確定（confidence = high）
   → ③ルール不一致 or 低信頼 → LLM分類へ
   → ④LLM分類（Claude API、構造化出力で 勘定科目/税区分/インボイス対応区分/confidence/reasoning を返す）
   → ⑤confidenceが閾値以上 → 自動確定
   → ⑤confidenceが閾値未満 → 人間レビューキューへ（例外処理のみ人手）
   → ⑥ユーザー修正があった場合 → ルール辞書に反映学習（フィードバックループ）
```

### 3.2 LLMの使い方（モデル選定とコスト最適化）

- **一次分類（大量・低難度）**: Claude Haiku 4.5（`claude-haiku-4-5`）。安価・高速で、大半の定型取引（サブスク、家賃、交通費等）を処理。
- **二次エスカレーション（低信頼・複雑ケース）**: Haiku の confidence が低い場合のみ、Claude Sonnet 5（`claude-sonnet-5`）または Opus 4.8（`claude-opus-4-8`）に再分類させる。判断が難しい按分（家事按分、消費税課税区分の判定等）はOpusクラスに寄せる。
- **バッチ処理**: 明細取り込みはリアルタイム性が不要なため、**Message Batches API（50%割引）**をデフォルト経路とする。ユーザーがアップロード直後に結果を見たい場合のみ同期呼び出しにフォールバック。
- **構造化出力**: `output_config.format`（json_schema）で「勘定科目コード／税区分／インボイス仕入税額控除可否／confidence（0-1）／根拠テキスト」を固定スキーマで返させ、パース失敗や表記ゆれを防ぐ。
- **プロンプトキャッシュ**: 勘定科目マスタ・税制ルール・過去の分類例（few-shot）をsystemプロンプトの先頭に固定し `cache_control` でキャッシュ、変動する取引明細のみ末尾に配置してキャッシュヒット率を最大化する。
- **レシート/請求書OCR**: 別建てのOCRサービス（Google Vision等）を挟まず、**Claudeのvision機能に直接レシート画像を渡し「OCR＋仕訳分類」を1回のAPI呼び出しで完結**させることで外部OCR費用を削減する（費用と精度はMVP検証で要トレードオフ確認）。

### 3.3 精度検証の仕組み

- **ゴールデンデータセット**: フリーランス・マイクロ法人それぞれについて、人手でラベル付けした仕訳サンプル（100〜300件程度、業種別に偏りが出ないよう収集）を作成し、`docs`外の非公開データストアで管理。
- **評価指標**: 自動確定率（confidence閾値以上で自動処理された割合）、正解率（自動確定分のうち勘定科目・税区分が正しい割合）、人間レビュー後の最終正解率、をダッシュボード化。business-planの成功指標（AI自動仕訳の正解率○○%以上）に直結させる。
- **回帰テスト**: プロンプト変更・モデル変更のたびにゴールデンセットで再評価し、精度劣化がないかCIで自動チェック（`ant`/Claude API `count_tokens`やBatch APIを使った夜間バッチ評価ジョブ）。
- **フィードバックループ**: ユーザーによる仕訳修正を全件ログ化し、（a）ルールベース辞書への反映、（b）月次でプロンプト改善・ゴールデンセット追加、の2系統で継続改善する。
- **税区分判定はルール優先**: インボイス制度の仕入税額控除可否や消費税課税区分など、誤りが直接的にコンプライアンスリスクにつながる項目は、LLM判定結果をそのまま確定させず「ルールベースの検証ロジック」を必ず通過させる（LLMは補助、最終判定はコード化されたルールが担保する設計）。

## 4. データセキュリティ・電子帳簿保存法対応の最低要件

### 4.1 電子帳簿保存法（電子取引データ保存 / スキャナ保存）

- **電子取引データ保存の真実性確保**: 以下いずれかの措置が必須。MVPでは「(b) 訂正・削除の履歴が残る、または訂正・削除ができないシステムで保存」を採用するのが実装コスト最小（タイムスタンプ付与サービスの外部契約が不要）。
  - (a) タイムスタンプ付与後のデータ授受、(b) 訂正削除履歴が残るシステムでの保存、(c) 訂正削除の防止に関する事務処理規程の備付け、のいずれか。
- **可視性確保**: 「取引年月日」「取引金額」「取引先」の3項目で検索できる機能が必須（DB側にインデックスを張り、検索UIを用意）。ディスプレイ・書面への出力機能も必須。
- **スキャナ保存（レシート等の紙原本を破棄する場合）**: 解像度200dpi相当以上、赤色・緑色・青色それぞれ256階調以上のカラー画像、タイムスタンプ付与または改ざん防止クラウドでの保存、入力者等の情報記録、が要件。MVPでレシートOCR機能を提供する場合は、この要件を満たすアップロード・保存フローを最初から設計する。
- **保存期間**: 個人事業主は原則5年（一部書類は7年）、法人は原則7年（欠損金がある事業年度は10年）。DB削除ポリシー・バックアップ保持期間をこれに合わせる。
- 要専門家レビュー: 上記は一般的な制度解説レベルの理解であり、**正式な運用開始前に税理士・弁護士によるチェックが必須**（business-planの要調査事項と同じ）。

### 4.2 データセキュリティ最低要件

- **通信の暗号化**: 全通信をTLS 1.2以上で暗号化（Cloudflare/Supabaseはデフォルトで対応）。
- **保存データの暗号化**: DB全体の暗号化（Supabase標準のat-rest暗号化）に加え、特に機微な項目（マイナンバー等の特定個人情報を万一保持する場合、所得金額等の税務データ）はカラムレベルでの追加暗号化を検討。
- **マイナンバー非保持の原則**: 本人送信方式（電子署名は本人のPC/スマホ上で完結）を徹底し、**SaaS側のサーバー・DBにはマイナンバー自体を一切保持しない設計**とする。これにより特定個人情報保護の負荷を大幅に下げられる（1.1章の結論と整合）。
- **アクセス制御**: Supabase Row Level Security（RLS）でテナント（ユーザー）ごとにデータアクセスを強制分離。管理者アクセスも最小権限・目的限定・操作ログ必須。
- **監査ログ**: 仕訳データ・申告書データへの全CRUD操作を改ざん不可能な形でログ化（追記専用テーブル or 外部ログサービス）。
- **個人情報保護法対応**: プライバシーポリシー整備、所得等の要配慮性が高い情報の取り扱い方針を明文化、第三者提供時の同意取得フロー。
